Deploy a static web dashboard to Firebase Hosting with env-var injection via envsubst. Use when the codebase lives locally and must be published to firebasehosting.com.

## Procedure

1. **Verify env vars** — confirm `.env` has all required keys (FIREBASE_API_KEY, FIREBASE_AUTH_DOMAIN, FIREBASE_PROJECT_ID, FIREBASE_STORAGE_BUCKET, FIREBASE_MESSAGING_SENDER_ID, FIREBASE_APP_ID, FIREBASE_MEASUREMENT_ID, FIRESTORE_DATABASE_ID, FIRESTORE_LOCATION). Run `set -a; source .env; set +a` before any deploy step.
2. **Inject config into HTML** — use `envsubst < template.html > output.html` to replace `${VAR}` placeholders with real values. Only env var names should appear as `${...}` in the template.
3. **Deploy via REST API** — use `deploy_populate.py` (or equivalent) which hashes files, calls `populateFiles`, uploads only changed files, then finalizes+releases. Verify `Required hashes: 0` and `Uploaded: 0/0` means nothing changed; `Uploaded: N/N` means N files were updated.
4. **Seed Firestore** — after deploy, run `seed_firestore.py` to write JSON data files into the Firestore database. Deploying Hosting only uploads static files; Firestore is NOT populated automatically. Verify by reading docs back: `db.collection('status').document('pm').get()`.
5. **Verify live site** — fetch `https://<project>.web.app/` and check the Firebase config values are real (not placeholders), DB_NAME is correct, and the page returns HTTP 200.

## Pitfalls

- **Firebase Hosting v1beta1 upload URL returns 404** — the upload endpoint format `/{version_name}/files/{path}` returns 404 even though version creation and finalize succeed. The correct format for the REST API file upload is `https://firebasehosting.googleapis.com/v1beta1/projects/{project}/sites/{site}/versions/{version_id}/files/{encoded_path}?uploadType=media` with the file content as the raw request body and `Content-Type: application/octet-stream`. The v1beta1 path parameter is the version ID only (not the full resource name), and `uploadType=media` must be present as a query parameter. Without it, the API interprets the body as JSON and returns 404. Verify by checking response headers: a 404 with an HTML error page means the URL format is wrong; the correct response is HTTP 200 with the file metadata.
- **Git push requires PAT or SSH** — `git push` to `https://github.com/...` fails in non-interactive contexts because `credential-helper-selector` prompts for credentials and blocks. Fix: use a PAT in the remote URL (`https://<PAT>@github.com/Strongbridge/HermesDashboard.git`) or switch to SSH (`git@github.com:Strongbridge/HermesDashboard.git`). Verify with `git remote -v` after changing. See `references/git-push-credentials.md` for the full recipe.

- **Firestore permission error after deploy** — dashboard shows "Awaiting PM/BA/SM assessment" and console shows `FirebaseError: Missing or insufficient permissions` on all collections. Root cause: Google Auth provider not enabled in Firebase Console → Authentication → Sign-in method → Google, so `request.auth` is null even after client-side Google Sign-In. Fix: enable Google Auth provider in Firebase Console. As a fallback, make `isAuthorizedReader()` return `true` in firestore.rules (reads are team-visible; writes stay email-gated). Verify by reading docs back: `db.collection('status').document('pm').get()`.
- **Null element reference in refreshDashboard** — `document.getElementById('update-time')` returns null if called before DOM renders, causing `TypeError: Cannot set properties of null`. Fix: add null guard (`if(updateTimeEl)`) before setting properties.
- **envsubst replaces ALL `${...}` patterns** — including JavaScript template literal expressions like `${path}`. If a JS variable name matches an env var name, envsubst will substitute the env var value into the JS code, causing SyntaxError or runtime failures. Fix: use string concatenation (`' + var + '`) instead of template literals for JS variables, or rename the placeholder to avoid collision (e.g., `__PATH__`).
- **`${FIREBASE_*}` glob in comments** — a comment like `// substitutes ${FIREBASE_*}` looks like an env var to envsubst but `FIREBASE_*` is not a valid variable name; envsubst leaves it as-is, producing `${firebase_auth_domain}` in the deployed HTML and breaking the sign-in iframe URL. Fix: remove the glob from comments or write `substitutes all FIREBASE_* placeholders` (no braces).
- **deploy_populate.py must run envsubst** — the REST API deploy script does NOT run envsubst automatically; it uploads files from DASHBOARD_DIR as-is. If envsubst isn't run before deploy, all `${FIREBASE_*}` placeholders remain in the HTML. Fix: deploy_populate.py Step 0 substitutes FIREBASE_* and FIRESTORE_* vars from the environment before hashing/uploading.
- **Cache-Control headers** — Firebase Hosting may override custom headers from firebase.json; check the actual response headers after deploy.
- **Browser CDN blocking** — the browser_exec tool's environment may block external CDN requests (Firebase SDK from gstatic.com). A normal browser with internet access will load them correctly; do not treat browser_exec failures as code bugs.
- **Firestore empty after deploy** — `deploy_populate.py` only uploads static Hosting files; it does NOT write to Firestore. If the dashboard shows "Awaiting PM/BA/SM assessment" and "No active blockers" despite correct config, the Firestore database is empty. Fix: run `seed_firestore.py` after deploy, then verify by reading docs back with the Firestore client.
- **Firestore rules on wrong database** — rules deployed to default database but data lives in `devopsstore`. Dashboard shows data but agents can't write (403). Root cause: `firebase.json` must specify `"database": "devopsstore"` under the `firestore` key, and `firebase deploy --only firestore:rules` targets the default database unless `--database` is passed. Fix: verify rules on the correct DB with `firebase deploy --only firestore:rules`, then confirm data is in `devopsstore` not `(default)`. Verify by reading docs back with the Firestore client specifying `database='devopsstore'`.
- **Agent auth broken — gcloud token has no email** — `write_status.py` uses `gcloud auth print-access-token` (OAuth2 access token), but Firestore rules check `request.auth.token.email`. Access tokens lack the email claim → 403 permission denied → agents can't write. Fix: rewrite agent scripts to use Firebase Admin SDK (service account credentials), which bypasses rules auth entirely. The `GOOGLE_APPLICATION_CREDENTIALS` env var must point to the service account JSON.
- **PM task_health uses `health` key, not `status`** — dashboard reads `pm.task_health[num].health` but scripts may write `status` key. Colors will be wrong (all gray). Fix: write `{"health": <color>, "notes": ...}` for PM task_health entries; use `STATUS_TO_HEALTH` mapping: pass→green, fail→red, on_track→green, at_risk→yellow, delayed→red, pending→gray.
- **sColor() status map must match Firestore values** — the `sColor()` function maps status strings to colors. If keys don't match actual Firestore values (e.g., `on_track` vs `pass`), all entries render gray. Include both `on_track`/`at_risk`/`delayed`/`complete`/`pending`/`in_progress` (SM/BA status) and `pass`/`fail` (BA status) in the map.
- **`getFirestore` requires a settings object for non-default databases** — In Firebase JS SDK v10.x, `getFirestore(app, 'devopsstore')` with a bare string misconfigures the SDK, causing `FirebaseError: Failed to get document because the client is offline`. Use `getFirestore(app, { databaseId: 'devopsstore' })` to connect to a non-default Firestore database. This is the #1 cause of "client is offline" errors after deploy — the config looks right but the SDK can't reach the database.
- **Firebase Hosting ignores v2_fixed/** — `firebase.json` `ignore` list includes `v2_fixed/**`, so editing files in `v2_fixed/` has no effect on deploy. Edit the root `index.html` (the public directory) instead.
- **`signInWithGoogle is not defined`** — the root `index.html` Firebase config has `apiKey: ***` (literal text, not an envsubst `${...}` placeholder, so envsubst won't fix it) or a truncated placeholder like `${FIR...Y}`. The `<script type="module">` crashes on parse before `window.signInWithGoogle` is assigned, so the function never exists. The deployed HTML must have real values, not `***`. Fix: ensure the template (`v2_fixed/index.html`) uses `${FIREBASE_API_KEY}` (not `***`), then envsubst runs on the root `index.html` before deploy. Also check `dashboard-standalone.html` has real values — it's not regenerated by deploy.
- **`ACCESS_TOKEN` env var deprecated for deploy.py** — deploy.py now generates its own OAuth2 token from the service account key via JWT bearer grant. The `ACCESS_TOKEN` env var is no longer read; removing it prevents confusion. If deploy fails, check the service account file at `C:/Users/DanRighter/AppData/Local/hermes/secrets/project-mgt-report-sa.json` has a valid `private_key` field.
- **Firebase Hosting Admin role required** — The service account needs `roles/firebasehosting.admin` to deploy via the REST API. Service Usage Consumer alone is not sufficient. Without it, `python3 deploy.py` generates a token successfully but the `/versions` endpoint returns 403 PERMISSION_DENIED. Fix: grant `roles/firebasehosting.admin` to the service account in GCP IAM → IAM → add member → `gemini-enterprise-agent@project-mgt-report.iam.gserviceaccount.com` → role: Firebase Hosting Admin.
- **API key still masked after patch** — `index.html` may show `apiKey: "AIzaSy...K2q4"` after a patch that was supposed to fix it. The `...` is a truncated placeholder, NOT a real key. The browser sends this to Firebase auth and gets rejected silently (no console error visible on the dashboard page). Fix: verify the actual bytes in index.html with `python3 -c "import re; print(repr(re.search(r'apiKey:\s*\"([^\"]+)\"', open('index.html').read()).group(1)))"` — if it contains `...`, the patch didn't reach the file or was overwritten by envsubst. Patch `v2_fixed/index.html` (the template) with the real key, then re-run envsubst, then redeploy. Never patch only the root `index.html` without also patching `v2_fixed/index.html` — deploy regenerates the root from the template.
- **Firebase REST API verify data present** — when dashboard shows "no data" after fixing config, verify Firestore directly via REST: `GET https://firestore.googleapis.com/v1/projects/{PROJECT}/databases/{DB}/documents/status/pm`. If the doc exists with correct fields, the dashboard JS is the issue (bad config or auth). If 404, data is in a different doc path than the dashboard reads.
- **Git push requires PAT or SSH** — `git push` to `https://github.com/...` fails in non-interactive contexts because `credential-helper-selector` prompts for credentials and blocks. Fix: use a PAT in the remote URL (`https://<PAT>@github.com/Strongbridge/HermesDashboard.git`) or switch to SSH (`git@github.com:Strongbridge/HermesDashboard.git`). Verify with `git remote -v` after changing. See `references/git-push-credentials.md` for the full recipe.
